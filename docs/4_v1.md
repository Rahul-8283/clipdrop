# Phase 4 — Discovery, Pairing & Sync Pipeline (v1)

## 1. Document Overview & Goals

### 1.1 Objective
Phase 4 connects the local core engine and transport layer into a fully autonomous, peer-to-peer synchronization system. It introduces out-of-band device pairing via Password-Authenticated Key Exchange (PAKE), zero-configuration local network discovery via mDNS, continuous peer presence monitoring, and the unified end-to-end event synchronization loop. Upon completing this phase, two separate physical machines (such as a MacBook and a Windows laptop) on the same Wi-Fi network can pair in seconds and automatically exchange clipboard contents in real time.

### 1.2 In-Scope Deliverables
- Ephemeral pairing server isolated from the primary transport listener.
- Pairing code generation adhering to human-readable phonetic formats (e.g., 4821-hawk-moon).
- Cryptographic PAKE handshake using schollz/pake v3 to derive a temporary symmetric key.
- Encrypted identity exchange (AES-GCM) exchanging certificate fingerprints, device names, and OS types.
- Automatic registration and deregistration of trusted devices via CLI commands: pair, pair join, devices, and unpair.
- Local discovery service broadcasting and browsing the _clipdrop._tcp mDNS service type via grandcat/zeroconf.
- Peer address resolution hierarchy: mDNS live cache, command-line --peer override, and stored last-known address.
- Presence monitor executing 5-second background pings and tracking online/offline state transitions.
- Complete bidirectional synchronization loop orchestrating clipboard watchers, engine filters, and transport pipelines.

### 1.3 Out-of-Scope (Non-Goals for Phase 4)
- No internet relaying, cloud tunneling, or Tailscale routing (strictly local subnet).
- No historical clipboard manager UI or long-term searchable index.
- No automated folder watching for screenshot files (M8 optional feature).
- No advanced system diagnostic commands (doctor command is scheduled for Phase 5).

## 2. Package Architecture & Responsibilities

### 2.1 Pairing Subsystem: netx/pairing/
- pairing_host.go: Implements the ephemeral pairing host listener, code expiration timer, and attempt counter.
- pairing_joiner.go: Implements the joiner client logic, mDNS pairing discovery, and PAKE negotiation.
- pake_session.go: Wraps schollz/pake v3 curves and cryptographic state calculations.
- credentials.go: Manages the encrypted exchange and validation of identity metadata over AES-GCM.

### 2.2 Discovery Subsystem: netx/discovery/
- announcer.go: Publishes local device presence, ports, and operational status to the local multicast subnet.
- browser.go: Listens for peer announcements, parses TXT records, and maintains an in-memory peer routing table.
- resolver.go: Translates peer device fingerprints into dialable IP:port socket addresses.

### 2.3 Application Coordination: app/
- Wires together the clipboard watcher, the discovery browser, the mTLS server, and the presence heartbeat into a unified runtime.
- Coordinates clean, orderly shutdown across all background worker routines via a root cancellation context.

## 3. PAKE Pairing Ceremony Specification

### 3.1 Security Philosophy
Clipdrop rejects pre-shared keys, passwords sent in plaintext, and manual certificate copying. Pairing must be frictionless for the user while remaining mathematically immune to passive eavesdropping and active man-in-the-middle (MITM) attacks on untrusted local networks.

### 3.2 Pairing Code Format & Constraints
- Structure: A short 4-digit numeric prefix joined with two phonetic dictionary words (format: NNNN-word-word, e.g., 8412-amber-falcon).
- Entropy: Provides sufficient search-space resistance against brute-force attacks within the active window.
- Expiration Window: The pairing session expires automatically after 120 seconds (2 minutes).
- Brute-Force Lockout: The host listener allows a maximum of 3 failed handshake attempts. Upon the third consecutive failure, the listener immediately terminates and drops state.
- Single-Use Guarantee: Once a pairing session completes successfully, the ephemeral listener terminates immediately and cannot be reused.

### 3.3 Host Workflow (clipdrop pair)
1. User executes clipdrop pair in the terminal.
2. The host engine generates a fresh pairing secret and initializes the PAKE host state.
3. The engine spins up an ephemeral HTTP server on a dynamically allocated port.
4. The host begins broadcasting an mDNS record with status attribute set to pairing.
5. The terminal prints the human-readable pairing code and initiates a 2-minute countdown timer.
6. The host waits for an incoming connection from the joiner.
7. Upon connection, both sides execute the PAKE mathematical point exchange.
8. If the exchange fails (wrong code), the failure counter increments; if 3 failures occur, the host exits with code 1.
9. If the exchange succeeds, both sides derive identical 256-bit symmetric session keys.
10. Using AES-GCM with the derived key, the host receives the joiner's identity (certificate fingerprint, hostname, OS) and responds with its own identity.
11. The host writes the joiner's details to trusted_devices.json with permissions 0600.
12. The ephemeral listener shuts down, mDNS pairing broadcast halts, and the console displays: "Paired with [joiner-name]".

### 3.4 Joiner Workflow (clipdrop pair join)
1. User executes clipdrop pair join in the terminal.
2. The terminal prompts the operator to input the pairing code displayed on the host.
3. The joiner queries the local network via mDNS for an active Clipdrop service advertising status=pairing (or uses the fallback --addr flag).
4. Upon locating the host, the joiner opens a TLS connection to the ephemeral pairing port.
5. Both sides execute the PAKE handshake using the operator-provided code.
6. If the code is incorrect, the handshake fails cryptographically, and the joiner prints a clear authentication error.
7. If successful, the joiner derives the symmetric session key, encrypts its local identity, and transmits it via AES-GCM.
8. The joiner receives and decrypts the host identity payload.
9. The joiner saves the host record into trusted_devices.json.
10. The console prints: "Paired with [host-name]".

## 4. Local Network Discovery via mDNS Zeroconf

### 4.1 Service Registration & Attributes
- Service Type: _clipdrop._tcp
- Domain: local.
- Port: Configured listening port of the node (default: 47820).
- Instance Name: Lowercase hexadecimal representation of the local device fingerprint (first 16 characters) combined with hostname.
- TXT Records:
  - id: Full SHA-256 fingerprint of the local device certificate.
  - name: User-configured or system hostname.
  - os: Operating system tag (darwin, windows, linux).
  - proto: Protocol version (currently "1").
  - status: Operational state ("ready" during normal run, "pairing" during active pair host).

### 4.2 Browser & Address Resolver
- The discovery browser continuously monitors the local subnet for _clipdrop._tcp service announcements and withdrawals.
- Discovered records are filtered against the local trusted_devices.json registry. Any discovered device that is not trusted is ignored.
- The resolver maintains an in-memory routing table mapping Device ID -> Active IP:Port.
- When an outbound transfer occurs, the resolver selects addresses according to the following strict priority:
  1. Active mDNS discovered IP and port (freshest network state).
  2. Manual CLI override flag (--peer ip:port), if provided.
  3. Last known recorded address stored in trusted_devices.json.
- If all three lookups fail, the item is dropped with a log notice: "peer offline, item dropped".

### 4.3 Network Interruption & Interface Changes
- If a laptop switches Wi-Fi networks, disconnects, or wakes from system sleep, the discovery subsystem detects network interface changes, tears down stale mDNS records, and re-announces the service on the newly active network interface.

## 5. Peer Presence & Heartbeat Monitoring

### 5.1 Heartbeat Loop Specification
- Every 5 seconds, the presence worker iterates through all entries in the trusted devices list.
- For each trusted device with a resolved network address, the worker issues an HTTP GET /v1/ping over mTLS.
- Status Transitions:
  - When a peer transitions from unreachable to reachable, the system logs: "Peer [name] is online ([ip:port])".
  - When a peer transitions from reachable to unreachable, the system logs: "Peer [name] went offline".
  - Successive pings during steady states produce zero log output, keeping terminal output clean.
- Upon every successful ping response, the worker updates the last_seen timestamp and last_address attribute in the trusted store.

## 6. End-to-End Synchronization Pipeline

### 6.1 The Complete Outbound Transfer Sequence
1. User copies text or captures a screenshot on Device A.
2. Platform clipboard watcher emits an event to the engine pipeline.
3. Engine reads, classifies, and validates the payload (PNG validation or UTF-8 check).
4. Engine computes SHA-256 checksum and confirms item is not an echo and not a duplicate.
5. Engine queries the discovery resolver for all trusted peers currently recorded as online.
6. If no peers are reachable, the engine logs "peer offline, item dropped" and resets state.
7. For each reachable peer, the client issues POST /v1/offer containing item metadata.
8. If the peer responds with action="skip", the transfer is aborted for that peer.
9. If the peer responds with action="send", the client streams raw payload bytes via PUT /v1/items/{id} with header X-Sha256.
10. Upon receiving HTTP 200 OK, the engine logs: "Sent [kind], [size] to [peer-name]".

### 6.2 The Complete Inbound Transfer Sequence
1. Server receives PUT /v1/items/{id} from a verified, mTLS-authenticated peer.
2. Server verifies raw payload size, computes streaming SHA-256, and validates PNG headers.
3. Server records payload SHA-256 digest into Last Received Hash in the engine.
4. Server invokes the platform clipboard Write method to apply the data to the OS pasteboard.
5. Server writes HTTP 200 OK response back to the sender.
6. Local clipboard watcher fires on the receiver machine due to the OS write.
7. Outbound engine inspects the change, recognizes that the content digest matches Last Received Hash, and drops the event without re-transmitting (preventing ping-pong loops).
8. The receiver terminal logs: "Received [kind], [size] from [peer-name]".

## 7. Concurrency & Goroutine Architecture

The complete system executes 5 synchronized background goroutines controlled by a single parent context:
1. Clipboard Watcher: Polls or listens for native OS pasteboard events.
2. Discovery Announcer: Maintains active mDNS multicast announcements.
3. Discovery Browser: Ingests multicast advertisements and maintains the peer address table.
4. Transport Server: Listens for incoming mTLS connections, offers, and payload uploads.
5. Presence Monitor: Dispatches 5-second health pings and updates device statuses.

All goroutines listen for context cancellation. When the user issues Ctrl+C, the root context cancels, all listeners stop taking new work, active transfers drain (up to 3 seconds), and the process exits cleanly.

## 9. Verification & Acceptance Testing Matrix

### 9.1 Automated Integration Tests
- PAKE Unit Test: Test successful key derivation when codes match. Test cryptographic failure when codes differ.
- Attempt Lockout Test: Execute 3 consecutive failed PAKE attempts against the ephemeral host. Verify host listener terminates automatically.
- Code Expiration Test: Verify ephemeral listener closes after simulated timeout expiration.
- Discovery Browser Test: Announce virtual zeroconf node. Verify browser parses TXT attributes and registers peer in routing table.
- Presence Ticker Test: Simulate peer going offline. Verify state transition log triggers once. Simulate recovery, verify online log triggers once.

### 9.2 Real Cross-Machine Acceptance Tests
- Scenario 1 (Pairing): Run clipdrop pair on Mac. Run clipdrop pair join on Windows. Enter code. Verify both sides print "Paired with [peer]" and both trusted_devices.json files reflect mutual trust.
- Scenario 2 (Image Sync): Capture a screenshot on Mac. Within 2 seconds, press Ctrl+V in Paint on Windows. Verify exact image pastes.
- Scenario 3 (Text Sync): Copy a URL on Windows. Within 1 second, press Cmd+V on Mac. Verify text pastes cleanly.
- Scenario 4 (Echo Loop Verification): Observe console output on both machines during image and text sync. Verify neither machine emits a return offer.
- Scenario 5 (Device Unpair): Run clipdrop unpair on Mac targeting the Windows laptop. Copy new content on Windows. Verify Mac rejects connection at TLS handshake and clipboard is unchanged.

## 10. Phase Completion Sign-Off
Phase 4 is complete when two real laptops can pair via a temporary code, discover each other automatically over local mDNS, exchange screenshots and text bidirectionally in under 2 seconds, reject unpaired devices, and run for 10 minutes without echo loops or process crashes.
