# Phase 1 — Foundation & CLI Skeleton (v1)

## 1. Document Overview & Goals

### 1.1 Objective
Phase 1 establishes the operational foundation for Clipdrop. The primary objective is to construct a production-grade, dependency-light Go binary skeleton that provides clean subcommand dispatch, standard logging, OS-compliant configuration management, and deterministic process lifecycle handling without implementing network or clipboard functionality yet.

### 1.2 In-Scope Deliverables
- Go toolchain configuration targeting Go 1.22+.
- Package organization aligning strictly with the root layout without an internal directory.
- CLI subcommand dispatch using the standard library flag package (strictly zero external CLI frameworks).
- Subcommand stubs for run, pair, pair join, devices, unpair, doctor, and version.
- Unified structured logging using standard library log/slog with configurable verbosity.
- Configuration directory locator and local setting manager respecting operating system conventions with strict permission isolation.
- Process lifecycle management including signal interception for graceful shutdown.

### 1.3 Out-of-Scope (Non-Goals for Phase 1)
- No clipboard polling, native event listening, or cgo integrations.
- No network transport, sockets, TLS configuration, or HTTP handlers.
- No mDNS announcements or discovery routines.
- No cryptographic key generation, certificate creation, or PAKE routines.

---

## 2. Package Architecture & Responsibilities

The codebase for Phase 1 introduces three primary components:

### 2.1 Entry Point: cmd/clipdrop
- Contains the main application entry point.
- Parses top-level arguments and routes execution to the registered subcommand handler.
- Handles top-level panics, unhandled errors, and emits standard process exit codes.
- Maintains zero business logic; serves solely as the CLI dispatcher.

### 2.2 Orchestrator: app/
- Manages application bootstrap, dependency wiring, and shutdown sequencing.
- Encapsulates execution state within an application runner construct.
- Manages parent Context propagation and signal cancellation listening (SIGINT, SIGTERM).
- Provides stub execution blocks for commands that will be expanded in later phases.

### 2.3 Configuration: config/
- Discovers the appropriate application state directory across supported platforms.
- Manages default configuration settings and flag-to-config parameter overrides.
- Enforces strict file access controls (read/write limited exclusively to the running user).

## 3. Command-Line Interface (CLI) Specification

### 3.1 Design Philosophy
To minimize external attack surface and binary weight, Clipdrop avoids heavy third-party CLI packages such as Cobra or Urfave CLI. Instead, it utilizes standard library flag sets partitioned per subcommand.

### 3.2 Command Routing Matrix

| Command Path | Arguments / Flags | Description |
|---|---|---|
| clipdrop version | None | Outputs semantic application version, commit hash, build date, and protocol version. |
| clipdrop run | --images-only, --no-text, --port, --peer, --verbose | Primary operational command. Runs the sync daemon in the foreground. |
| clipdrop pair | --port, --verbose | Initiates host pairing mode, launching an ephemeral listener. |
| clipdrop pair join | --addr, --verbose | Prompts for a pairing secret and connects to an active host. |
| clipdrop devices | --verbose | Enumerates all trusted peer devices recorded in the local store. |
| clipdrop unpair | [device-name-or-id] | Revokes trust for a specified peer device. |
| clipdrop doctor | --verbose | Runs diagnostic routines on host network, permissions, and configuration. |

### 3.3 Flag Specifications for "run"
- --images-only (Boolean): When enabled, suppresses text sync and restricts processing exclusively to PNG images.
- --no-text (Boolean): Functional alias for --images-only to ensure intuitive operator ergonomics.
- --port (Integer): Specifies the listener port for mutual TLS transport. Default: 47820.
- --peer (String): Manual host:port address override for networks where multicast DNS is filtered.
- --verbose (Boolean): Elevates the global log level from INFO to DEBUG.

### 3.4 Process Exit Codes
- Exit 0: Clean execution, intentional termination via SIGINT/SIGTERM, or successful command completion.
- Exit 1: General execution failure, unhandled runtime error, or invalid parameter combinations.
- Exit 2: Command-line parsing error, missing required arguments, or unknown subcommands.
- Exit 130: Interrupted by operator (standard POSIX SIGINT code).

## 4. Configuration & State Management

### 4.1 Storage Location Rules
All application data, certificates, and runtime metadata must reside within an isolated user directory derived via standard user configuration directory APIs:
- macOS: /Users/[username]/Library/Application Support/clipdrop
- Windows: C:\Users\[username]\AppData\Roaming\clipdrop
- Linux (for developer environments): /home/[username]/.config/clipdrop

### 4.2 Permission Isolation
Clipdrop handles sensitive private keys and device pairing records. Therefore, filesystem permissions must be strictly guarded:
- Base configuration directory: Must be created with mode 0700 (owner read, write, execute only).
- All generated files: Must be created or updated with mode 0600 (owner read, write only).
- The application must verify these permission attributes upon startup and emit a warning or error if lax permissions are detected.

### 4.3 Default Settings Structure
The configuration manager exposes the following default attributes:
- Device Name: Hostname of the local machine (customizable via configuration).
- Default Listen Port: 47820.
- Max Image Size: 25 Megabytes (26,214,400 bytes).
- Max Text Size: 1 Megabyte (1,048,576 bytes).
- Peer Heartbeat Interval: 5 seconds.
- Connect Timeout: 3 seconds.
- Offer Timeout: 3 seconds.
- Upload Timeout: 15 seconds.

## 5. Logging Architecture

### 5.1 Technology Standard
All logging across Clipdrop uses the standard library log/slog package. Third-party logging libraries (such as zap, logrus, or zerolog) are explicitly disallowed.

### 5.2 Formats and Handlers
- Interactive Terminal (TTY): Emits human-readable text output with clear timestamps, log levels, and contextual key-value attributes.
- Non-Interactive / Scripted: Structured key-value text or JSON lines if standard output is redirected.
- Error Stream Separation: Operational status is sent to stdout; errors and diagnostics are sent to stderr.

### 5.3 Privacy and Data Hygiene
Under no circumstances may raw clipboard content, decrypted text payloads, or sensitive pairing secrets be logged at any level (including DEBUG). Only metadata may be recorded:
- Permitted attributes: Payload size in bytes, MIME type, SHA-256 fingerprint, peer ID, duration in milliseconds.
- Prohibited attributes: Raw text bytes, image pixel data, full pairing codes, unencrypted authentication tokens.

---

## 6. Process Lifecycle & Signal Handling

### 6.1 Lifecycle Flow
1. Entry point initializes top-level context with signal cancellation.
2. Signal listener attaches to os.Interrupt (SIGINT) and syscall.SIGTERM.
3. Subcommand router parses CLI arguments and prepares the runtime environment.
4. If invalid arguments are supplied, command usage is printed and process exits with code 2.
5. If valid, the target handler runs with the signal context.
6. Upon receipt of termination signal, the context cancels, prompting children to abort in-flight work.
7. The process waits for active routines to finish (budgeted up to 3 seconds) before exiting cleanly.

## 7. Build System & Toolchain Configuration

### 7.1 Compiler & Toolchain
- Go Version: 1.22 or higher.
- Cgo Requirements: macOS requires Xcode Command Line Tools for downstream Cocoa clipboard APIs. Windows requires no C compiler.
- Target Module Path: github.com/[username]/clipdrop.

### 7.2 Compilation Commands
- Development build: Native compilation targeting host operating system.
- Race detection: All test execution must be validated with the Go race detector enabled.

## 9. Verification & Quality Acceptance Criteria

### 9.1 Unit Testing Requirements
- Test configuration directory path resolution on all supported operating systems.
- Test that created directories strictly observe 0700 permission bits on Unix-like systems.
- Test subcommand parser with valid inputs, invalid flags, missing arguments, and help requests.
- Test that the logger correctly switches levels between INFO and DEBUG based on flags.

### 9.2 Manual Acceptance Test Scenarios
- Scenario 1: Run "clipdrop version" on macOS and Windows. Verify formatted output and exit code 0.
- Scenario 2: Run "clipdrop --unknown" or "clipdrop run --invalid". Verify meaningful error, usage guide, and exit code 2.
- Scenario 3: Run "clipdrop run" in foreground, emit Ctrl+C (SIGINT). Verify immediate log message noting shutdown and exit code 0.
- Scenario 4: Run "clipdrop run --verbose". Verify that debug-level logs appear on console.
- Scenario 5: Verify that the configuration directory is created on disk at the expected path with restricted permissions.

---

## 10. Phase Completion Sign-Off
Phase 1 is complete when all manual test scenarios succeed on both a macOS host and a Windows host, the test suite executes with zero failures under race detection, and no clipboard, transport, or pairing code has been prematurely introduced.
