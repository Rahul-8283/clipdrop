# Phase 3 — Identity & Transport Security (v1)

## 1. Document Overview & Goals

### 1.1 Objective
Phase 3 establishes the cryptographic identity and secure transport layer for Clipdrop. It defines how each device generates and protects its public-key credentials, implements a decentralized certificate-pinning trust model, and constructs a mutual TLS 1.3 (mTLS) HTTP transport pipeline. By the end of this phase, two Clipdrop instances can mutually authenticate, verify peer identity, exchange health pings, evaluate transfer offers, and securely stream clipboard payloads without relying on any external Certificate Authority (CA) or cloud infrastructure.

### 1.2 In-Scope Deliverables
- Cryptographic identity generation: ECDSA P-256 private key and self-signed X.509 certificate.
- Device ID derivation via SHA-256 digest of the raw DER certificate bytes.
- Strict filesystem permission enforcement (mode 0600) for stored private keys and certificates.
- Persistent trusted-devices registry backed by atomic JSON writes.
- Mutual TLS 1.3 client and server configuration with custom fingerprint validation callbacks.
- Protocol endpoint implementation: GET /v1/ping, POST /v1/offer, and PUT /v1/items/{id}.
- Enforcement of protocol headers (X-Proto-Version, X-Sha256) and strict operational timeouts.
- Comprehensive in-process integration test demonstrating secure transfers and untrusted peer rejection.

### 1.3 Out-of-Scope (Non-Goals for Phase 3)
- No out-of-band PAKE pairing ceremonies (trust records are seeded manually in tests).
- No automatic local network discovery via mDNS.
- No live operating system clipboard reads (uses fake clipboard or mock buffers for payload verification).
- No file archiving of received items to the history folder.

## 2. Package Architecture & Responsibilities

### 2.1 Identity Management: identity/
- Responsible for inspecting the local configuration directory for existing credentials.
- Generates new ECDSA P-256 private keys and corresponding self-signed X.509 certificates on first initialization.
- Calculates and formats canonical device identifiers (SHA-256 certificate fingerprints).
- Loads PEM-encoded keys and certificates into standard library crypto structures.

### 2.2 Trust Store: store/
- Manages the trusted_devices.json state file in the application configuration directory.
- Provides thread-safe read, insert, update, and deletion operations for trusted peer records.
- Guarantees crash-resilient atomic file writes (writing to temporary files and renaming).
- Exposes query methods to quickly check whether a presented certificate fingerprint is trusted.

### 2.3 Secure Transport: netx/transport/
- Server: Configures and runs a standard library net/http server wrapped in an mTLS 1.3 listener.
- Client: Constructs a hardened http.Client configured with client-side certificates and peer certificate verification hooks.
- Protocol Engine: Handles route dispatching, JSON payload serialization, hash verification, and HTTP status code mappings.

## 3. Device Identity & Cryptographic Primitives

### 3.1 Key Generation Standards
- Algorithm: Elliptic Curve Digital Signature Algorithm (ECDSA).
- Curve: NIST P-256 (secp256r1). P-256 provides strong 128-bit security levels while ensuring ultra-low computational overhead on mobile and laptop processors.
- Key Storage: Encoded as PKCS#8 or SEC1 in PEM format. Stored on disk as key.pem.

### 3.2 Self-Signed Certificate Generation
- Format: X.509 Version 3 certificate.
- Serial Number: Cryptographically random 128-bit integer.
- Subject: Common Name set to the local device hostname.
- Validity Duration: 10 years (long-lived local credential).
- Key Usage: Digital Signature and Key Agreement.
- Extended Key Usage: Server Authentication and Client Authentication.
- Storage: PEM-encoded certificate stored on disk as cert.pem.

### 3.3 Device ID & Fingerprint Computation
- The canonical Device ID is defined strictly as the SHA-256 hash of the certificate's raw ASN.1 DER-encoded byte sequence.
- Display Format: Lowercase hexadecimal representation (64 characters).
- This fingerprint serves as the immutable address and identity token across all protocol interactions.

### 3.4 Filesystem Protection & Permissions
- Key and certificate files must be written with filesystem mode 0600 (read/write restricted exclusively to the owner).
- Before loading keys at startup, the identity loader checks file permissions. On Unix-like systems, if permissions allow group or world read access, startup is halted with a clear remediation message.

## 4. Trust Model & Persistence

### 4.1 Decentralized Pinned Trust (No External CA)
Clipdrop bypasses conventional hierarchical PKI. There are no root certificates, intermediate authorities, or public trust anchors. Trust is strictly peer-to-peer:
- A peer is trusted if and only if its certificate fingerprint exists in the local trusted_devices.json registry.
- During the TLS handshake, Clipdrop inspects the peer certificate directly, extracts its SHA-256 fingerprint, and checks the local database.

### 4.2 Trusted Devices Schema (trusted_devices.json)
Each entry in the trusted store maintains the following attributes:
- Device ID: Hexadecimal SHA-256 fingerprint of the peer certificate (primary key).
- Device Name: Human-readable hostname of the peer device.
- Operating System: Operating system classification (e.g., darwin, windows, linux).
- Paired At: RFC3339 timestamp recording initial trust establishment.
- Last Seen: RFC3339 timestamp updated upon successful ping or item receipt.
- Last Address: Most recent IP address and port where the peer was reached.

### 4.3 Atomic File Persistence
To prevent database corruption during sudden system shutdowns or power loss:
- Updates are written to a sibling temporary file (e.g., trusted_devices.json.tmp).
- Flushed and synchronized to disk via operating system sync commands.
- Atomically renamed over the destination file.
- Access is coordinated via an in-memory sync.RWMutex.

## 5. Mutual TLS 1.3 Implementation

### 5.1 TLS Handshake Configuration
Both communicating laptops act simultaneously as TLS servers and TLS clients:
- MinVersion / MaxVersion: Explicitly pinned to TLS 1.3 (tls.VersionTLS13). Legacy protocols (TLS 1.0, 1.1, 1.2) are disabled.
- Cipher Suites: TLS 1.3 default secure suites (TLS_AES_128_GCM_SHA256, TLS_CHACHA20_POLY1305_SHA256).

### 5.2 Server-Side Peer Authentication
- ClientAuth: Set to RequireAnyClientCertificate. The server forces every incoming connection to provide a client certificate.
- VerifyPeerCertificate Hook: Standard CA chain validation is bypassed. The custom verification function:
  1. Inspects the raw certificates presented by the client.
  2. Computes the SHA-256 hash of the peer leaf certificate.
  3. Queries the trust store.
  4. If the fingerprint is recognized, the connection is admitted.
  5. If the fingerprint is unrecognized, the handshake is aborted immediately, and a security warning is logged with the offending fingerprint.

### 5.3 Client-Side Peer Authentication
- InsecureSkipVerify: Set to true only to bypass default root CA chain lookups.
- VerifyPeerCertificate Hook: Mirrors the server-side verification:
  1. Computes the SHA-256 digest of the server's leaf certificate.
  2. Rejects the connection if the server certificate does not match a trusted peer.

## 6. Sync Protocol & Endpoints Specification

### 6.1 Required Protocol Headers
- X-Proto-Version: Must equal "1". Any request with a missing or mismatched version is rejected with HTTP 400 Bad Request.
- X-Sha256: Present on payload uploads. Represents the lowercase hexadecimal SHA-256 digest of the payload body.

### 6.2 Endpoint: GET /v1/ping
- Purpose: Lightweight peer health check and presence monitoring.
- Request: Empty body.
- Response Status: 200 OK.
- Response Body: JSON object containing:
  - device_name (string): Hostname of the responding device.
  - protocol_version (integer): Value must be 1.
  - current_time (string): RFC3339 timestamp.

### 6.3 Endpoint: POST /v1/offer
- Purpose: Solicits approval from a peer before transmitting heavy payload bytes.
- Request Body: JSON object containing:
  - id (string): Unique transfer UUIDv4.
  - kind (string): Classification, either "image" or "text".
  - size (integer): Payload size in bytes.
  - sha256 (string): SHA-256 digest of the content.
  - mime (string): MIME type ("image/png" or "text/plain; charset=utf-8").
- Evaluation Rules on Receiver:
  - If kind is "text" and receiver is configured with --images-only: Reply "skip", reason: "kind_disabled".
  - If size exceeds 25MB for images or 1MB for text: Reply "skip", reason: "too_large".
  - If sha256 equals the receiver's current clipboard content: Reply "skip", reason: "duplicate".
  - Otherwise: Reply "send".
- Response Status: 200 OK.
- Response Body: JSON object containing:
  - action (string): "send" or "skip".
  - reason (string): Empty if sending, or one of "duplicate", "too_large", "kind_disabled", "paused".

### 6.4 Endpoint: PUT /v1/items/{id}
- Purpose: Binary streaming upload of the offered clipboard item.
- Headers: X-Sha256 (required), Content-Type (required).
- Request Body: Raw binary bytes streamed over the connection.
- Receiver Processing:
  1. Checks transfer size against strict stream limits (rejects stream if bytes read exceed 25MB).
  2. Computes running SHA-256 digest while reading the stream into memory.
  3. Verifies computed digest matches X-Sha256 header and earlier offer.
  4. If kind is image, executes imaging package PNG validation.
  5. Returns HTTP status code.
- Response Codes:
  - 200 OK: Content accepted and successfully verified.
  - 400 Bad Request: Missing headers, invalid PNG bytes, or malformed request.
  - 413 Payload Too Large: Byte stream exceeds configured maximum bounds.
  - 422 Unprocessable Entity: Computed SHA-256 digest does not match X-Sha256 header.

### 6.5 Network Timeouts
All transport connections use strict timeouts to guard against hanging routines:
- Connect Timeout: 3 seconds.
- Offer Exchange Timeout: 3 seconds.
- Payload Upload Timeout: 15 seconds.

## 8. Verification & Acceptance Testing Matrix

### 8.1 Automated In-Process Integration Tests
- Two-Node Handshake Test: Spawn Server A and Server B on loopback ports with distinct identities. Register A in B's trust store and B in A's trust store. Execute PingPeer and verify 200 OK.
- Untrusted Peer Rejection Test: Spawn Server C with a rogue identity not present in Server A's store. Client C attempts to call GET /v1/ping on Server A. Verify connection is rejected during TLS handshake and error is returned to client.
- Offer Skip Test (Duplicate): Client A offers item X to Server B. Mock Server B's clipboard hash to equal item X. Verify Server B returns action "skip" with reason "duplicate".
- Offer Accept and Upload Test: Client A offers new image item Y. Server B returns "send". Client A streams item Y via PUT /v1/items/{id}. Verify Server B validates SHA-256 and replies 200 OK.
- Hash Mismatch Rejection Test: Client A uploads payload with an intentionally corrupted X-Sha256 header. Verify Server B rejects with HTTP 422 Unprocessable Entity.
- Oversized Payload Test: Client A attempts to upload 26MB stream. Verify Server B truncates read and terminates with HTTP 413.

### 8.2 Concurrency & Security Tests
- Run complete test suite with go test -race ./...
- Verify zero memory leaks or unclosed HTTP response bodies across sequential transfers.
