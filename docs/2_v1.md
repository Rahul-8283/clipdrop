# Phase 2 — Local Core: Clipboard, Imaging & Engine (v1)

## 1. Document Overview & Goals

### 1.1 Objective
Phase 2 builds the local data processing engine for Clipdrop. It establishes a platform-agnostic clipboard abstraction, strict payload validation for images and text, and an echo-proof event processing pipeline. By the end of this phase, the application can monitor the local operating system clipboard, detect new screenshots and text copies, validate and normalize payloads, compute cryptographic digests, and completely eliminate self-echo loops without requiring any live network components.

### 1.2 In-Scope Deliverables
- Unified clipboard abstraction interface defining Read, Write, and Watch semantics.
- Real platform clipboard wrapper utilizing golang.design/x/clipboard with OS-specific build tags.
- High-fidelity in-memory fake clipboard for deterministic, zero-dependency unit tests.
- Imaging validation package verifying PNG signatures, dimensions, and memory safety.
- Text normalization ensuring valid UTF-8 encoding and size enforcement.
- Engine event processor managing change detection, SHA-256 digest computation, and deduplication.
- State-driven echo loop prevention mechanism tracking recently applied remote items.
- Policy enforcement honoring command-line restrictions (--images-only and --no-text).

### 1.3 Out-of-Scope (Non-Goals for Phase 2)
- No peer discovery via mDNS.
- No network transport, mTLS sockets, or HTTP endpoints.
- No pairing handshakes or PAKE authentication.
- No persistent storage of items to disk (received folder archiving is deferred).

## 2. Package Architecture & Responsibilities

### 2.1 Platform Abstraction: platform/clipboard/
- clipboard.go: Declares the canonical Clipboard interface, custom content types, and error types.
- clipboard_real.go: Implements the interface using native OS hooks wrapped by golang.design/x/clipboard. Uses build tags for darwin and windows environments.
- clipboard_fake.go: Implements a purely in-memory clipboard emulator with thread-safe read/write operations and event notification channels for automated testing.

### 2.2 Payload Validation: imaging/
- Performs fast byte-level validation on incoming image data.
- Enforces strict PNG compliance, reading binary chunk headers without decoding unneeded raster scanlines into RAM.
- Verifies image dimensions (width, height) to guard against pixel flood attacks or decompression bombs.

### 2.3 Core Pipeline: engine/
- Acts as the central event hub connecting the clipboard watcher to outbound preparation.
- Manages local deduplication (ignoring identical copies made in rapid succession).
- Implements the echo suppression state machine (preventing locally applied remote clips from triggering a bounce-back transfer).
- Applies operational filtering based on size boundaries and configured CLI flags.

## 3. Clipboard Abstraction Specification

### 3.1 Interface Contract
The platform layer exposes a clean interface that decouples OS-specific APIs from the core engine:
- Read: Fetches current clipboard content, returning an abstract payload containing raw bytes, payload type (Text or Image), and MIME classification.
- Write: Injects raw bytes into the operating system clipboard, accepting content type parameters.
- Watch: Accepts a cancellation context and returns a read-only channel emitting events whenever local clipboard contents mutate.

### 3.2 Supported Formats
- Text: Plain text representation encoded strictly as UTF-8. Rich text formats (RTF), HTML formatting, and proprietary office document structures are flattened or filtered.
- Image: Raster graphic data encoded strictly as portable network graphics (PNG). Other formats (JPEG, BMP, TIFF, WebP) are rejected or must be converted before propagation.

### 3.3 Platform-Specific Behaviors & Quirks
- macOS (Darwin): Uses Cocoa pasteboard APIs (NSPasteboard) via cgo. Requires main-thread synchronization or explicit runloop event processing. Permissions for Accessibility or Screen Recording are not required for basic clipboard reads, but system alerts may surface on newer macOS releases.
- Windows: Uses Win32 user32 clipboard APIs. Clipboard opening can intermittently fail if another desktop utility holds an active lock. The wrapper must implement brief retry backoff (up to 3 attempts across 50 milliseconds) before failing.

### 3.4 Fake Clipboard Specification (for Testing)
The in-memory test double must faithfully reproduce real-world OS semantics:
- Internal storage guarded by a read-write mutex.
- Non-blocking channel broadcasts whenever Write is executed.
- Configurable error injection hooks (e.g., simulating locked clipboard, read failures).
- Zero dependencies on cgo or platform-native GUI subsystems.

## 4. Imaging & Payload Normalization

### 4.1 PNG Validation Rules
Clipdrop is screenshot-centric. Screenshots placed on system clipboards must be verified before any network transmission is considered:
- Magic Signature: Bytes 0 to 7 must strictly match the 8-byte PNG file signature: 137, 80, 78, 71, 13, 10, 26, 10.
- IHDR Chunk Extraction: The first critical chunk must be IHDR. The validator extracts image width and height as 32-bit big-endian unsigned integers.
- Dimension Guardrails: Maximum width and height are bounded at 16,384 pixels each. Images exceeding this threshold are rejected.
- Size Limits: Image payloads must not exceed 25 Megabytes (26,214,400 bytes).

### 4.2 Text Validation Rules
- Encoding: Must be valid UTF-8. Non-UTF-8 byte sequences are detected and rejected.
- Content Check: Empty strings or whitespace-only inputs are ignored at the source.
- Size Limits: Text payloads must not exceed 1 Megabyte (1,048,576 bytes).

### 4.3 Policy Enforcement
The engine checks runtime flags before accepting clipboard events:
- If --images-only or --no-text is active, any detected text event is silently dropped before hashing.
- If payload size exceeds configured bounds, a descriptive warning is emitted via slog and the event is dropped.

## 5. Core Engine & Echo Loop Prevention

### 5.1 The Echo Loop Dilemma
In bidirectional peer-to-peer synchronization, when Device A sends a clipboard update to Device B, Device B writes the content to its local OS clipboard. The OS clipboard watcher on Device B immediately fires, interpreting this write as a new local copy event. If uncontrolled, Device B will re-broadcast the same item back to Device A, creating an infinite, bandwidth-consuming loop.

### 5.2 The Hash & Origin State Model
To eliminate this feedback loop completely, the engine maintains an internal synchronization registry:
- Current Local Hash: SHA-256 digest of the current local clipboard content.
- Last Received Hash: SHA-256 digest of the item most recently applied to the clipboard from a remote peer.
- Last Local Sent Hash: SHA-256 digest of the item most recently dispatched to outbound peers.

### 5.3 Outbound Processing Pipeline
When the local clipboard watcher fires:
1. Event Ingestion: Watcher emits an event indicating a change occurred.
2. Read & Classify: Engine invokes clipboard Read. If empty or inaccessible, the event is abandoned.
3. Policy Check: Evaluates content type against active flags (--images-only, --no-text).
4. Validation: Passes raw bytes through imaging or text validator. Drops invalid payloads.
5. Digest Computation: Calculates SHA-256 checksum over the raw bytes.
6. Echo Check: Compares calculated digest against Last Received Hash. If digests match, the event is recognized as a self-echo caused by a remote write. The engine suppresses the event and halts processing.
7. Deduplication Check: Compares digest against Last Local Sent Hash. If identical, the user simply copied the same item twice. The event is suppressed.
8. State Update: Updates Last Local Sent Hash.
9. Dispatch Readiness: Passes validated, normalized payload to the outbound queue (connected to transport in Phase 4).

### 5.4 Inbound Processing Pipeline (Contract for Downstream Phases)
When a remote peer sends an item (simulated in Phase 2 tests):
1. Inbound item is received and payload digest (SHA-256) is confirmed.
2. The engine records this digest in Last Received Hash BEFORE invoking clipboard Write.
3. The engine invokes clipboard Write.
4. When the local OS watcher subsequently fires, the Outbound Pipeline steps through and terminates at step 6 because the hashes match.

## 6. Concurrency & Goroutine Orchestration

### 6.1 Threading Model
- Watcher Goroutine: Dedicated loop listening to operating system clipboard events. Terminates immediately when the root Context is cancelled.
- Engine Event Loop: Reads from the watcher channel, processes incoming items sequentially through validation and hashing, and updates state safely.
- State Synchronization: Access to Last Received Hash and Last Local Sent Hash is protected by sync.RWMutex to prevent race conditions during concurrent incoming transfers and local copy actions.

## 8. Verification & Acceptance Testing Matrix

### 8.1 Unit Tests (Automated via Fake Clipboard)
- Echo Loop Test: Simulate applying an item from a peer. Trigger the fake watcher. Verify the engine suppresses dispatch and no outbound event is produced.
- Deduplication Test: Copy item X, verify outbound dispatch. Copy item X a second time, verify suppression.
- Flag Restriction Test: Enable --images-only. Copy text item, verify immediate suppression. Copy PNG image, verify outbound dispatch.
- Size Limit Test: Copy a 26MB image. Verify engine drops item and logs warning.
- Non-PNG Image Rejection: Inject JPEG magic bytes into image copy. Verify validator rejects payload.
- Concurrency Race Test: Run all unit tests with go test -race ./... to verify zero race conditions between watcher and inbound apply routines.

### 8.2 Manual Acceptance Tests
- Scenario 1 (macOS Screenshot): Take an interactive screenshot with Cmd+Ctrl+Shift+4. Verify console logs indicate valid PNG detection with correct dimensions and SHA-256 digest.
- Scenario 2 (Windows Screenshot): Take a screenshot with Win+Shift+S. Verify console logs report valid PNG detection.
- Scenario 3 (Plain Text Copy): Copy a paragraph of text. Verify console logs indicate text classification and correct byte count.
- Scenario 4 (Rapid Copy): Press Ctrl+C three times on the same snippet. Verify the engine logs one detection and two deduplications.
