# Phase 6 — End-to-End Testing & Verification (v1)

## 1. Document Overview & Goals

### 1.1 Objective
Phase 6 represents the final validation gate for Clipdrop v1. It specifies the comprehensive testing methodology, cross-platform physical test matrices, fault injection scenarios, adversarial security checks, and performance benchmarks required to certify the software for production release. The core goal is validating that Clipdrop satisfies all Definition of Done criteria across real physical hardware (macOS and Windows laptops) under real-world network conditions.

### 1.2 In-Scope Deliverables
- Full codebase race condition audit utilizing the Go race detector.
- Automated multi-node loopback integration tests validating concurrent transfers and state isolation.
- Physical cross-platform test matrix executed between macOS and Windows devices on shared Wi-Fi.
- Echo loop resilience certification (10 minutes of continuous bidirectional traffic with zero loops).
- Security boundary penetration tests (unpaired intruder rejection, payload tampering, brute-force lockout).
- Network fault injection tests (Wi-Fi disconnections, IP address changes, system sleep/wake recovery).
- Performance benchmarking evaluating transfer latency, idle CPU usage, and memory consumption.
- Formal sign-off verification against the Section 12 Definition of Done.

### 1.3 Out-of-Scope (Non-Goals for Phase 6)
- No testing across more than two concurrently paired devices (v1 scope is strictly two laptops).
- No testing over cellular hotspots or corporate VPN tunnels with Tailscale.
- No automated UI/GUI driving (verification uses native OS pasteboard and terminal assertions).
- No backward compatibility testing with legacy protocol versions (v1 is the baseline).

---

## 2. Testing Strategy & Philosophy

### 2.1 The Testing Pyramid
Testing in Clipdrop transitions through three distinct layers:
1. Pure Unit Tests: Validates discrete functions (PNG headers, flag parsing, hash calculations, JSON persistence) in total isolation.
2. Simulated Loopback Integration: Spawns multiple in-process Clipdrop nodes on localhost communicating over real TCP and mTLS sockets to test protocol coordination.
3. Physical End-to-End (E2E) Testing: Operates compiled native binaries on separate physical machines (one macOS laptop, one Windows laptop) communicating over real Wi-Fi.

### 2.2 The Zero-Mock Invariant for Phase 6
While earlier phases used an in-memory fake clipboard double for speed and isolation, Phase 6 demands testing against the real operating system clipboard (cgo Cocoa pasteboard on macOS and Win32 user32 pasteboard on Windows). Mocked networks and fake clipboards are strictly disallowed in final acceptance testing.

## 3. Concurrency & Race Verification Suite

### 3.1 Race Detection Audit
- Execution Standard: All package test suites must be executed with the Go race detector enabled across all platforms.
- Requirement: Zero data race warnings across all packages (app, config, identity, platform, imaging, engine, netx, store, doctor).
- Target Scenarios:
  - Concurrent incoming upload occurring simultaneously with a local clipboard copy action.
  - Presence ping worker reading the routing table while mDNS browser updates an IP address.
  - Termination signal (SIGINT) received during active binary payload streaming.

### 3.2 Goroutine Leak Auditing
- Baseline Verification: After startup, the application stabilizes at exactly 5 persistent background worker routines.
- Transfer Test: Dispersing 100 sequential offer and upload operations must return the active goroutine count to the baseline once idle.
- Shutdown Verification: Emitting a cancellation signal must terminate all 5 background routines within 3 seconds, leaving zero orphan routines before process exit.

## 5. Adversarial & Security Boundary Tests

### 5.1 Intruder Rejection Test
- Objective: Verify that an unpaired third device cannot connect, ping, offer, or upload data to paired nodes.
- Execution: Launch a third laptop (Node C) on the same Wi-Fi with an independently generated self-signed certificate. Direct Node C to issue requests to Node A and Node B.
- Expected Outcome: Both Node A and Node B reject the connection during the TLS 1.3 handshake inside the custom VerifyPeerCertificate callback. The connection terminates with an alert, and an audit warning is emitted. Zero data enters the pipeline.

### 5.2 Payload Tampering & Hash Defense
- Objective: Verify that corrupted or maliciously modified network payloads are rejected without clipboard pollution.
- Test Scenarios:
  1. Alter payload byte in transit: Server detects SHA-256 mismatch against X-Sha256 header and rejects with HTTP 422 Unprocessable Entity.
  2. Spoofed PNG header: Upload file with valid 8-byte PNG signature but corrupted IHDR chunk. Imaging validator fails, server returns HTTP 400 Bad Request.
  3. Oversized payload stream: Stream 26MB of raw bytes. Server truncates stream upon exceeding 25MB boundary and returns HTTP 413 Payload Too Large.

### 5.3 Pairing Ceremony Attack Resistance
- Scenario 1 (Code Expiration): Launch host pair mode. Wait 121 seconds. Attempt to join. Joiner fails to authenticate because the host listener has closed.
- Scenario 2 (Brute-Force Lockout): Launch host pair mode. Submit 3 consecutive incorrect pairing codes from joiner. Verify the host listener terminates immediately on the third failure and refuses further connections.

## 6. Fault Injection & Network Resilience Tests

### 6.1 Wi-Fi Disconnection & Network Roaming
1. Start active sync between Mac and Windows.
2. Disconnect Wi-Fi on Windows for 15 seconds.
3. Verify Mac presence monitor detects absence and logs: "Peer [windows] went offline".
4. Reconnect Wi-Fi on Windows (simulating DHCP lease renewal with a new IP address).
5. Verify mDNS discovery announces new IP, Mac resolves new address, and logs: "Peer [windows] is online".
6. Copy new screenshot; verify sync succeeds immediately without restarting either binary.

### 6.2 System Sleep & Wake Cycle Recovery
1. Put Mac laptop into deep system sleep (close lid) for 60 seconds while Windows remains active.
2. Wake Mac.
3. Verify background routines refresh sockets, re-announce mDNS, and resume heartbeat pings within 5 seconds.
4. Execute copy operation; confirm immediate transfer.

### 6.3 Mid-Transfer Abrupt Disconnection
1. Begin uploading a 20MB image payload from Node A to Node B.
2. Kill Node A (SIGKILL) mid-transfer.
3. Verify Node B catches EOF / connection reset cleanly, drops the partial buffer, writes zero bytes to the local clipboard, and returns to idle listening without panicking.

## 7. Performance & Resource Benchmarks

### 7.1 Latency Benchmarks
- Screenshot Sync Latency: Time elapsed from local copy completion on Node A to clipboard write readiness on Node B must not exceed 2.0 seconds for images up to 5MB over local Wi-Fi.
- Text Sync Latency: Time elapsed from local copy to remote paste readiness must not exceed 500 milliseconds for text clips under 50KB.

### 7.2 System Resource Footprint
- Idle Memory (Resident Set Size): Memory usage while in foreground idle monitoring must remain below 35 Megabytes.
- Memory Stability: Memory usage after 50 consecutive screenshot transfers must return to within 5MB of baseline (zero unbounded heap accumulation).
- CPU Utilization: Idle CPU consumption across all 5 background goroutines must register below 1.0% on both macOS and Windows.

## 9. Definition of Done Final Sign-Off

The final release of Clipdrop v1 is officially signed off when all 5 conditions from Section 12 of the build specification are met:
1. Fresh Installation Verification: On a fresh Mac and fresh Windows laptop on the same Wi-Fi, the operator can build, pair once, run, copy a screenshot on one, and paste on the other in under 2 seconds, in both directions.
2. Text Parity: Plain text copy and paste operates bidirectionally with sub-second latency.
3. Echo Loop Immunity: Zero echo loops or duplicate pastes occur during a minimum of 10 minutes of active, continuous operation.
4. Zero-Trust Boundary: An unpaired third device is rejected at the TLS handshake and cannot connect or transfer data.
5. Codebase Health: go test -race ./... passes cleanly across the entire repository, and the README provides comprehensive setup instructions in under 10 steps.
